# Security model and release gates

PassVault is an offline native iOS/Android app. No server, analytics, account, cloud backup, or remote recovery. Build tools download dependencies; the shipped app does not need a network connection.

## Guarantees and limits

The vault must only persist authenticated ciphertext. A random data key is wrapped using a password-derived key and a device-bound secret. Biometrics release a separately protected copy of the data key through the OS, not a UI-only authentication flag. A successful biometric unlock (Android strong biometrics, iOS Face ID / Touch ID through the Secure Enclave) resets the failed-password counter, as the app password does. Exports require the app password again, even after biometric unlock; that check is a counted attempt toward the 10-failure limit. On Android, encrypted backups are encrypted with that same app password (fresh Argon2id salt per file) and deliberately do not depend on the originating device, so an exported file is only as strong as the app password against offline guessing. To make each guess costlier without asking for a second password, new backups use Argon2id at 256 MiB and 4 passes (the local vault uses 64 MiB and 3 passes because it is also guarded by the device secret and attempt limit); the cost is stored in the authenticated header, bounded on read, and older backups still open. Changing the app password does not re-encrypt earlier backups, and a backup made under an old password stays attackable with that old password.

Physical possession or a USB cable must not expose plaintext through app file sharing, Android backup, logs, or unencrypted databases. This does not imply protection against every OS exploit: a compromised process or operating system can capture secrets while they are in use. StrongBox availability varies by Android device. Root/jailbreak detection cannot establish trust.

10 consecutive failed app-password attempts trigger cryptographic erasure. Reserve an attempt durably before checking the password, serialize all authentication, and fail closed on missing/corrupt state. A process termination during verification consumes an attempt. Neither platform offers arbitrary offline apps a universal rollback-proof monotonic counter, but each blocks the practical file-level rollback. On iOS the state lives in the Keychain, which restoring app files cannot rewind. On Android every state write that records an attempt, a vault change or a password change moves to a new Keystore key and deletes the old one, so copying the state file before guessing and restoring it afterwards no longer works: the restored file's key is gone and access is refused. What remains is an attacker who can rewind the Keystore itself or use the app's keys directly (root, a debuggable build, a full-device or hardware-level snapshot); that defeats software counters on any platform. No offline portable backup can enforce an attempt limit against someone making copies. Do not advertise an unbypassable counter.

Erasure destroys the local decryption keys; flash wear leveling prevents a promise of physical overwrite. Independently exported files are not erased. CSV exports are plaintext and cannot require a password when another application opens them. Wrong encrypted-backup passwords reject that import; they do not erase the existing vault.

Swift/Kotlin strings, UI bindings, and managed arrays can leave transient copies in process memory. Clearing references and overwriting mutable buffers is best effort, not a guarantee of complete memory zeroization. Android clipboard clearing can be delayed or prevented if the OS stops the process; receiving apps can retain copied values. iOS cannot universally prevent screenshots of an active app. The privacy cover protects inactive scenes, not a compromised compositor.

Android window hardening: `FLAG_SECURE` (no screenshots or recents thumbnails), the whole UI is excluded from autofill services and content capture, other apps' overlays are hidden while the app is visible (API 31+), and touches are ignored while an untrusted window covers the app. Seed-phrase editors never write to the clipboard.

Android autofill (opt-in): the autofill service holds no key and returns only a locked suggestion. The vault is unlocked in a separate hardened activity (same window protections), with the same counted attempts, and locked when it fills, is left, or the screen turns off. Every selected login requires an explicit destination confirmation showing the app label, actual package name and claimed website. App names, package-name hints and the browser-name list only rank suggestions; they do not verify app signatures or ownership of a website. No app is silently trusted, including a browser whose package name is on the list. A filled value is handed to the requesting app, which can keep it. Website ranking uses the bundled Public Suffix List, including private hosting suffixes; IP addresses are compared as complete literals and ambiguous host encodings are refused. The selected fields must report the same origin; an unrelated first node or a parent frame cannot supply the destination of another frame's fields.

All Android vault engines and protected-storage entry points share one process-wide reentrant lock. It covers whole authentication and storage transactions, including password derivation and atomic-file commit, so status checks cannot see a reserved tenth attempt as a completed failure or discard another writer's pending state. The autofill service queues its status check off the main thread. The main and autofill screens also initialize storage in the background.

An open engine records which vault blob it loaded. If another window saves newer records, rotates the vault key, removes the decoy or erases the vault, a stale session cannot overwrite that state with an older snapshot or key; it must unlock again. Biometric setup owns and clears its derived key even when derivation finishes after a lock or cancellation. Biometric callbacks from a stopped or locked screen are ignored, and the autofill screen prevents copying the typed app password to the system clipboard.

Debug builds are debuggable: with USB debugging enabled on an unlocked phone, `adb run-as` can act as the app (including using its Keystore keys) and a debugger can read its memory. Keep valuable data only in a signed release build.

While one of the app's own system pickers (import/export file chooser) is open, auto-lock uses a fixed 2-minute grace period instead of the chosen timeout, so leaving the app from inside a picker still locks the vault. App passwords must be at least 12 characters, because encrypted backups use the same password and can be attacked offline without an attempt limit. The data key is zeroed when the activity is destroyed.

With a 1- or 5-minute auto-lock, Android may freeze the app in the background and deliver the screen-off event late, so on return the vault can appear for a moment before locking. The elapsed-time check on return still enforces the timeout; choose "Immediately" to avoid this.

Imports from other password managers run entirely on the device and never write the source file anywhere. Their parsers are bounded (16 MiB of records; compressed data may not inflate past a fixed limit) and refuse what they do not understand rather than guessing. The XML reader used for KeePass refuses any DOCTYPE, so external entities and entity expansion (XXE, "billion laughs") cannot apply. KeePass databases are checked against every hash and MAC the format carries before use, and a wrong password or key file is reported as such. Opening a KeePass database derives its key with the database's own settings (Argon2 up to 512 MiB, AES-KDF up to 2 billion rounds); settings beyond that are refused instead of exhausting the phone. Android uses BouncyCastle's lightweight API for Argon2d and the ChaCha20 / Salsa20 key streams; iOS implements Argon2 (checked against the RFC 9106 test vectors and libsodium) and uses libsodium, CommonCrypto and Apple's Compression framework. Import files stay plaintext wherever the user saved them: delete them after checking the import.

A decoy vault is a second wrapped data key and vault file in the same protected state, opened by its own password. It is meant for being forced to unlock the app, not for hiding from forensic analysis: the state and the second ciphertext file show that a second vault exists to anyone who examines the device, and the source code is public. To keep the unlock screen from revealing it, every password unlock derives two Argon2id keys (the decoy's, or a throwaway one when there is no decoy), which roughly doubles unlock time for everyone. A successful decoy password leaves the failed-attempt counter where it was, so alternating decoy sign-ins with guesses cannot extend the 10-attempt limit; only the real password at unlock, or biometrics (which always open the real vault), clears it. While the decoy vault is open, export and the current-password check of a password change accept only the decoy's password, and the settings that would reveal or change the real vault (biometrics, decoy setup) are not shown. Changing the decoy's password from inside it refuses the real password as the new one, which tells whoever tries it that they guessed the real password; that refusal counts as a failed attempt. An accepted change also tells them their guess was wrong, so successful decoy password changes, which cost no attempt, are limited to three until the real password or biometrics opens the vault; further changes are refused, never erased. The real vault can give the decoy a new password, keeping its entries, for when the decoy password is forgotten: at setup the real vault makes an X25519 key pair, keeps its secret key sealed under the real vault's data key, and the decoy's data key is kept in a libsodium sealed box to that public key. The decoy can replace that box when its own password changes but cannot open it. Erasure removes both vaults.

Phone-to-phone transfer needs no network. Sending requires the app password (a counted attempt). The vault is compressed and then encrypted (no attacker-controlled input is mixed in, so compression does not leak anything) under a random 12-character one-time code with Argon2id at the local vault's cost; at about 59 bits, guessing the code from a recorded QR stream or a copied transfer file is impractical. The QR frames and the file carry only ciphertext; the code is shown only when the user asks, and the QR code is hidden while it is, so a single photo or screen recording never captures both. Someone who records the QR stream and also sees the code can open the transfer. So that the file can be shared through another app, the code and the sealed transfer stay in memory for up to 10 minutes after leaving PassVault (shown again only after unlocking the same vault); turning the screen off or locking the phone discards them. AirDrop and Quick Share move a transfer file over a direct device-to-device link rather than the local network, and the file stays encrypted either way.

File encryption (Android) uses age v1 (c2sp.org/age). The key is a secure-note entry in the vault, so it is protected exactly as the vault is: on the phone by the app password, device secret and attempt limit; in a backup by the app password and Argon2id, which is then the only offline attack on every encrypted file. An encrypted file has no password of its own and cannot be guessed. New keys are post-quantum hybrid (ML-KEM-768 + X25519 via HPKE); a file is exposed only if both are broken. File names and approximate sizes are not hidden. Decrypted copies and originals left in shared storage are plaintext; the app offers to delete the original after encrypting and reminds the user after decrypting. Payload damage is detected chunk by chunk, so failed or cancelled output is emptied and deleted rather than left as a partial plaintext. The age code is new and has not been audited; it is checked against the official test kit. Details: [FILE-ENCRYPTION.md](FILE-ENCRYPTION.md).

## Cryptography

The local vault uses libsodium Argon2id v1.3 (64 MiB, 3 iterations, 1 lane, 32-byte key) and XChaCha20-Poly1305 (256-bit key, random 192-bit nonce, 128-bit authentication tag). Encrypted backups (`QVAULT02`) use the same construction at 256 MiB and 4 iterations, with the cost in an authenticated header that readers bound to 64 MiB to 1 GiB and 3 to 10 iterations; `QVAULT01` files (64 MiB, 3 iterations) still import. The cipher suite is fixed by the format version, which prevents algorithm confusion; input sizes and header costs are bounded before expensive work. Passwords are normalized to Unicode NFKC before use, so the same typed text works across keyboards and across iOS and Android; older data keyed from the text exactly as typed is accepted once and re-wrapped. Changing the app password also replaces the data key and re-encrypts the vault, and turns biometric unlock off until it is enabled again. There is no single “most secure” encryption algorithm: these are established choices, not a claim that newer means stronger.

Sources: [libsodium password hashing](https://doc.libsodium.org/password_hashing/default_phf), [XChaCha20-Poly1305](https://doc.libsodium.org/secret-key_cryptography/aead/chacha20-poly1305/xchacha20-poly1305_construction), [Apple Keychain](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web), [Android Keystore](https://developer.android.com/privacy-and-security/keystore).

## Required before release

- Compile and run both apps on real devices, including biometric enrollment changes, cancellation, device restart, backgrounding, and process death.
- Verify no plaintext appears in files, backups, recent-app snapshots, crash reports, logs, or exported temporary files.
- Exercise all 10 attempts, concurrent unlock/export, interrupted state writes, deleted state, restored old ciphertext, reinstall, and key invalidation.
- Verify import/export interoperability, malformed files, authentication failures, CSV escaping, and legacy custom-field variants with sanitized fixtures.
- Benchmark Argon2id on the minimum supported devices, including the 256 MiB backup profile; never silently lower cost.
- Audit dependencies, native binary provenance, accessibility, and distribution signing. Obtain an independent security review before storing valuable credentials or publishing security claims.
- Check Android native library 16 KiB page-size compatibility and final merged release manifest; no Internet permission or backup path should be introduced transitively.
